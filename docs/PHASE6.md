# Phase 6: integrations and scheduling: what is built and what is not

docs/SPEC.md Phase 6 asks for Google OAuth (Search Console, GA4, URL Inspection), scheduled audits with
email/Slack/webhook regression alerts, Jira/Linear/Trello push with status sync, and optional log upload. Its gate:
"connected test property shows traffic per URL; scheduled audit sends a correct regression alert; tickets round-trip
status."

Only the part that needs no third-party account is built: **scheduled audits with signed webhook regression
alerts**. Everything else needs real accounts or credentials. It is **not built and its gates are not passed**. No
stub or mock stands in for any of it.

| Spec item | Status | Gate |
| --- | --- | --- |
| Scheduled audits (daily, weekly, monthly) | Built | `npm run gate:p6` |
| Webhook regression alert, HMAC-signed | Built | `npm run gate:p6` |
| Email (SMTP) and Slack alerts | Not built: needs an SMTP account / Slack app | Not passed |
| Google OAuth, GSC columns and discovery, URL Inspection, GA4 | Not built: needs a Google Cloud OAuth client and a verified test property | Not passed |
| Jira, Linear, Trello push with status sync | Not built: needs accounts and API tokens | Not passed |
| Log upload with reverse-DNS Googlebot verification | Not built | Not passed |

## Scheduled audits

- **A schedule** belongs to a site. It holds the audit request the New audit form would send (without basic auth: a
  stored password would be another secret to manage) and a timing: daily, weekly on a weekday, or monthly on day
  1–28. The day is capped at 28 so every month has it. All times are UTC
  (`src/lib/schedule/cadence.ts`, unit-tested).
- **Launching.** `src/instrumentation.ts` starts a tick in each Node.js server instance: every `SCHEDULER_TICK_MS`,
  default 60 s. `SCHEDULER=off` disables it on an instance, and it only runs with `CRAWLER_V2=true`. Each tick claims
  the due schedules with `FOR UPDATE SKIP LOCKED`, and moves their next run in the same transaction. So several
  instances never launch one slot twice. Each claimed schedule is launched through `launchAudit`, the New audit
  path. The launch, or its error, is recorded in `schedule_runs`.
- **Missed slots are not caught up.** A server that was down for a week runs a weekly schedule once when it comes
  back, not once per missed slot. Resuming a paused schedule moves it to the next slot after now.
- **Run now** sets the next run to now. The tick picks it up within a minute.

## Regression alert

After the analysis worker analyses a crawl that a schedule launched, `src/lib/schedule/deliver.ts`:

1. Finds the site's previous analysed audit (the same rule the Compare screen uses).
   - **None:** records `skipped` ("First analysed audit").
2. Compares the two (`compareCrawls`).
   - **No issue group is new or regressed:** records `skipped`. Resolved, persistent and not-re-checked groups never
     alert.
3. Otherwise builds the alert and POSTs it:
   - The body is the `RegressionAlert` JSON (`src/lib/schedule/alert.ts`): the site, both audits, the health
     score before and after, the totals per change, and the new and regressed groups with fingerprint counts.
     Regressed groups come first.
   - The header is `x-sitesentry-signature: sha256=<hex HMAC-SHA256 of the raw body>`. Receivers verify it with
     `verifySignature` (constant-time).
   - The request goes through the crawler's SSRF guard: the host is resolved once, private and reserved addresses
     are refused, and the socket is pinned to the vetted address. Redirects are not followed.
   - A failed request is retried up to 3 times; 5xx, 408, 429 and network errors are retried, any other 4xx is not.
   - Every outcome (`sent`, `failed`, `skipped`) is stored in `alert_deliveries`, unique per schedule and crawl. A
     retried analysis job therefore never alerts twice.
   - The schedule's site page lists the outcomes under **Alerts**.

The **signing secret** is generated by the server when the schedule is created. It is returned once, in the create
response, and the UI shows it once. It is stored encrypted with `CRAWLER_SECRET_KEY` (AES-256-GCM, scoped to the
schedule id). A webhook therefore needs that key on both the app and the worker.

`APP_URL`, when set on the worker, adds a link to the audit's Compare screen to the alert.

## API

| Method and path | Does |
| --- | --- |
| `GET /api/[ws]/schedules?site=` | List (never includes the secret) |
| `POST /api/[ws]/schedules` | Create: `{ siteId, cadence, hourUtc, weekday?, monthday?, request, webhookUrl? }`; returns `{ schedule, webhookSecret }` |
| `PATCH /api/[ws]/schedules/[id]` | `{ enabled }` pauses or resumes; `{ runNow: true }` |
| `DELETE /api/[ws]/schedules/[id]` | Delete, with its runs and deliveries |
| `GET /api/[ws]/schedules/[id]/deliveries` | The last 50 alert outcomes |

Deleting a site deletes its schedules.

## Gate (local part)

`npm run build && npm run gate:p6` runs a schedule of the fixture's `/meta/` section (Custom profile, subfolder
scope) against the production app, a real worker and a local webhook receiver. There are three runs, each started
with Run now and launched by the app's tick:

1. Fix patch off: no alert (first audit).
2. Fix patch on: no alert (groups only resolve).
3. Fix patch off: exactly one alert, with **META-003 regressed**.

The alert's signature must verify with the secret returned at creation. Its groups, fingerprint counts and totals
must equal the Compare API's for the same two audits.

Tests: `src/lib/schedule/cadence.test.ts` and `alert.test.ts` (unit), and `schedule.int.test.ts` (Postgres: claim
once, alert once, the skip and failure paths, and a private address refused before any request).
